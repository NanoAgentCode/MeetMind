# 会智录项目学习路线

这份路线面向希望从“能启动项目”逐步达到“能独立扩展系统”的开发者。学习内容以当前代码为准，不要求先完整学习所有框架再开始实践。

## 1. 学习目标

完成路线后，你应该能够：

1. 解释一次会议录音从上传到导出的完整数据流。
2. 修改 React 页面、调用后端接口并处理异步状态。
3. 使用 FastAPI 新增接口、定义数据模型和处理业务异常。
4. 理解 RustFS 中录音、会议元数据和导出文件的对象结构。
5. 区分 ASR 与 LLM，配置真实语音转写服务。
6. 使用 LangGraph 修改纪要生成工作流。
7. 接入 OpenAI、Claude、Ollama 或 vLLM 模型协议。
8. 编写测试并完成构建、联调和故障定位。

## 2. 项目全景

先记住一条主链路：

```text
React 页面
  ↓ 上传录音
FastAPI 接口
  ↓ 保存对象
RustFS
  ↓ 读取临时音频
ASR 语音转写
  ↓ 转写文本
LangGraph 纪要工作流
  ↓ 结构化 Minutes
人工修改与定稿
  ↓
Word / Markdown 导出并保存到 RustFS
```

建议按以下顺序阅读项目：

1. `README.md`：运行方式和系统边界。
2. `src/App.tsx`：用户看到的完整业务流程。
3. `src/api.ts`：前端与后端之间的接口契约。
4. `backend/app/main.py`：后端接口和状态流转。
5. `backend/app/models.py`：会议与纪要的数据结构。
6. `backend/app/store.py`：RustFS 对象存储实现。
7. `backend/app/services.py`：转写和 LangGraph 工作流。
8. `backend/app/providers.py`：多模型协议适配。
9. `backend/tests/`：系统行为的可执行说明。

## 3. 推荐学习周期

建议周期为 6 周，每周投入 6—10 小时。如果已经熟悉 React 或 Python，可合并对应阶段。

| 周次 | 主题 | 阶段产物 |
|---|---|---|
| 第 1 周 | 环境、Git 与项目主流程 | 本地运行并画出请求链路 |
| 第 2 周 | React 与 TypeScript | 独立修改上传和纪要编辑页面 |
| 第 3 周 | FastAPI 与数据模型 | 新增一个经过测试的接口 |
| 第 4 周 | RustFS、ASR 与文件处理 | 验证对象上传、读取和导出 |
| 第 5 周 | LangChain、LangGraph 与多模型 | 接入至少一种真实模型 |
| 第 6 周 | 测试、联调与部署 | 完成一次完整验收演示 |

## 4. 第一阶段：运行并理解主流程

### 4.1 需要掌握

- Git 的提交、分支和远程仓库基础。
- Node.js、npm、Python 虚拟环境的作用。
- HTTP 请求、JSON、表单上传的基本概念。
- Docker Compose 的服务、端口、环境变量和数据卷。

### 4.2 实践步骤

1. 启动 RustFS：

   ```powershell
   docker compose up -d rustfs
   ```

2. 启动后端：

   ```powershell
   cd backend
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   Copy-Item .env.example .env
   uvicorn app.main:app --reload
   ```

3. 启动前端：

   ```powershell
   npm install
   npm run dev
   ```

4. 使用演示模式完成一次：上传 → 转写 → 生成 → 修改 → 导出。
5. 打开 `http://localhost:8000/docs`，手动调用健康检查接口。
6. 登录 RustFS 控制台，确认会议对象已经写入存储桶。

### 4.3 验收标准

- 能说出 5173、8000、9000、9001 四个端口的用途。
- 能在浏览器、FastAPI 文档和 RustFS 控制台中找到同一次会议的数据。
- 能解释 `demo` 模式为什么不能识别真实录音。

## 5. 第二阶段：React 与 TypeScript 前端

### 5.1 学习重点

- React 函数组件和 `useState`、`useMemo`。
- TypeScript 接口、联合类型和泛型请求结果。
- Ant Design 的 `Upload`、`Input`、`Button`、`Empty`。
- Axios、`FormData` 和文件上传。
- 异步加载、成功提示和错误提示。
- 响应式 CSS 与移动端布局。

### 5.2 对照代码

- `src/types.ts`：`Meeting`、`Minutes`、`MeetingStatus`。
- `src/api.ts`：所有后端请求。
- `src/App.tsx`：页面状态和阶段操作。
- `src/styles.css`：编辑台视觉与响应式规则。

### 5.3 实践任务

1. 为上传区域增加文件大小和扩展名的前端提示。
2. 为“生成纪要”按钮增加二次确认。
3. 在工作区显示当前会议状态和创建时间。
4. 将重复的加载与错误处理提取为自定义 Hook。

### 5.4 验收标准

```powershell
npm run build
```

- TypeScript 构建无错误。
- 上传前按钮禁用，选择合法文件后启用。
- 后端返回错误时，页面能够显示可理解的提示。
- 390px 宽度下页面没有横向溢出。

## 6. 第三阶段：FastAPI 与业务状态

### 6.1 学习重点

- 路由、路径参数、查询参数和表单文件。
- Pydantic 模型与输入校验。
- HTTP 状态码和 `HTTPException`。
- Python 异步函数及外部 HTTP 调用。
- 会议状态机：

  ```text
  uploaded → transcribed → generated → edited → export
  ```

### 6.2 对照代码

- `backend/app/main.py`：接口与状态流转。
- `backend/app/models.py`：数据模型。
- `backend/app/config.py`：环境变量配置。
- `backend/tests/test_flow.py`：完整业务流程测试。

### 6.3 实践任务

新增“会议列表”接口：

```text
GET /api/meetings
```

建议依次完成：

1. 先编写失败测试，定义排序和返回字段。
2. 为存储层增加按前缀列出会议元数据的能力。
3. 实现 FastAPI 接口。
4. 运行全部测试，确认原流程没有回归。

### 6.4 验收标准

- 能解释为什么未转写时不能生成纪要。
- 能为错误的状态跳转选择合适的 4xx 状态码。
- 新接口有测试，而不是只在 Swagger 中手动验证。

## 7. 第四阶段：RustFS 与文件处理

### 7.1 学习重点

- 对象存储与本地文件系统的差异。
- S3 的 bucket、key、object、content type。
- path-style addressing 和访问凭证。
- 流式上传、临时文件及大文件内存风险。
- Word 和 Markdown 导出的内容组织。

### 7.2 当前对象结构

```text
huizhi-meetings/
├── recordings/{meeting_id}/source.{ext}
├── meetings/{meeting_id}.json
└── exports/{meeting_id}/minutes.{docx|md}
```

### 7.3 对照代码

- `docker-compose.yml`：RustFS 本地服务。
- `backend/app/store.py`：S3 客户端和对象路径。
- `backend/app/exporter.py`：Word、Markdown 生成。

### 7.4 实践任务

1. 使用 RustFS 控制台检查每个阶段产生的对象。
2. 故意填写错误密钥，观察并定位上传失败。
3. 为 `MeetingStore` 增加导出文件读取测试。
4. 研究如何将当前整文件读入内存改为分片或流式上传。

### 7.5 验收标准

- 能根据会议 ID 推导三个对象路径。
- RustFS 不可用时，接口不会错误地返回“上传成功”。
- 能解释为什么生产环境不能保留示例访问密钥。

## 8. 第五阶段：ASR 语音转写

### 8.1 先区分两个概念

- ASR：把音频转换为文字。
- LLM：根据转写文字生成摘要、决策和行动项。

模型协议支持 OpenAI、Claude、Ollama、vLLM，指的是纪要生成模型；它们不会自动替代 ASR。

### 8.2 对照代码

- `backend/app/services.py` 中的 `transcribe_audio`。
- `backend/.env.example` 中的 `ASR_BACKEND`、`ASR_MODEL`。

### 8.3 实践任务

1. 配置 OpenAI-compatible ASR 服务。
2. 使用一段 1—3 分钟的真实录音测试识别结果。
3. 对比普通话、数字、英文缩写和多人发言场景。
4. 记录响应时间、识别错误和文件格式差异。

### 8.4 进阶方向

- 发言人分离。
- 时间戳和字幕分段。
- 自定义热词。
- 长音频切片和失败重试。
- 实时 WebSocket 转写。

## 9. 第六阶段：LangChain、LangGraph 与多模型协议

### 9.1 学习重点

- LangChain Chat Model 的统一调用接口。
- LangGraph 的 State、Node、Edge、START 和 END。
- Prompt 中的结构化输出约束。
- Pydantic 对模型 JSON 的最终校验。
- 云端模型与本地模型的配置差异。

### 9.2 对照代码

- `backend/app/providers.py`：模型 Provider 工厂。
- `backend/app/services.py`：LangGraph 节点与纪要生成。
- `backend/tests/test_providers.py`：各协议配置测试。
- `backend/tests/test_minutes_generation.py`：模型输出规范化测试。

### 9.3 Provider 对照

| Provider | 协议 | 典型用途 |
|---|---|---|
| `openai` | OpenAI | 直接使用云端模型 |
| `anthropic` | Claude 原生协议 | 使用 Claude 系列模型 |
| `ollama` | Ollama HTTP | 本机快速运行开源模型 |
| `vllm` | OpenAI-compatible | GPU 服务器部署开源模型 |
| `demo` | 本地规则 | 无密钥演示和自动测试 |

### 9.4 实践任务

1. 先使用 `demo` 阅读完整图执行流程。
2. 接入 Ollama 或一个云端模型，生成同一份会议纪要。
3. 比较不同模型输出的摘要、决策和行动项。
4. 在 LangGraph 中新增“纪要质量检查”节点：

   ```text
   generate_minutes → validate_minutes → END
   ```

5. 当行动项缺少负责人或时间时，让检查节点返回明确提示。

### 9.5 验收标准

- 切换 Provider 时不需要修改业务代码。
- 模型返回非 JSON 内容时，系统能明确报错。
- 能用图解释当前工作流，而不是只会调用 LangChain。
- 新增节点后有成功与失败测试。

## 10. 第七阶段：测试与质量保证

### 10.1 测试层次

1. 单元测试：Provider 构造、模型输出解析、导出函数。
2. 接口测试：上传校验和状态跳转。
3. 流程测试：上传到导出的完整闭环。
4. 集成测试：连接真实 RustFS、ASR 和 LLM。
5. 浏览器测试：用户操作与响应式界面。

### 10.2 常用命令

```powershell
cd backend
pytest -q

cd ..
npm run build
```

### 10.3 实践任务

- 为超大文件、空文件和错误扩展名补充测试。
- 为错误 Provider、缺少密钥和非法模型 JSON 补充测试。
- 模拟 RustFS 不可用，检查接口响应。
- 使用 Playwright 自动完成一次前端上传操作。

### 10.4 验收标准

- 修复 Bug 前先编写能够复现问题的测试。
- 新增功能同时包含正常路径和至少一个失败路径。
- 不把“测试没报错”当成真实外部服务已联调成功。

## 12. 推荐扩展顺序

掌握当前第一阶段后，建议按价值和依赖关系继续开发：

1. 会议列表与历史记录。
2. 任务进度查询，避免长请求阻塞。
3. 转写文本人工纠错。
4. 发言人识别和时间戳。
5. 纪要模板与自定义 Prompt。
6. 用户登录和会议权限。
7. 实时录音与 WebSocket 字幕。
8. 全文搜索和会议知识库。

不要直接从实时转写开始。先保证会后闭环稳定，再引入音频分片、连接恢复和增量状态等复杂问题。

## 13. 最终综合练习

独立实现“会议历史与重新生成”功能：

1. 首页展示历史会议列表。
2. 可以重新打开某次会议。
3. 可以修改模型 Provider 后重新生成纪要。
4. 旧版定稿仍保存在 RustFS，生成新版本对象。
5. 为版本切换、错误 Provider 和 RustFS 写入失败编写测试。
6. 更新 README 和功能文档。

完成后，你应能从前端操作、API、工作流、模型协议和存储对象五个角度解释该功能，并用测试结果证明它确实可用。
