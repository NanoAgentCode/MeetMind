# 会智录系统学习手册

本文面向接手会智录项目的开发者，目标是从“能够运行系统”逐步达到“能够定位问题、修改功能并安全扩展”。内容以当前代码为准，建议边读代码边完成每章练习。

## 1. 当前系统能力

会智录是一个基于 React、FastAPI 和 LangGraph 的 AI 会议纪要系统，当前主流程为：

```text
上传会议录音
  → ASR 语音转写
  → LangGraph 生成结构化纪要
  → 人工修改并保存定稿
  → 导出 Word / Markdown
```

系统已经支持：

- 企业工作台风格的会议处理页面。
- 会议记录列表、搜索、状态筛选、打开详情和删除。
- OpenAI-compatible ASR API。
- OpenAI、Anthropic Claude、Ollama、vLLM 四种纪要模型协议。
- SQLite 持久化会议元数据、转写和纪要。
- RustFS 保存原始录音和导出文件。
- RustFS 存储桶不存在时自动创建。
- 后端流程测试和前端 TypeScript 生产构建。

当前不包含实时麦克风转写、发言人分离、用户登录和多租户权限。

## 2. 学习完成目标

完成本手册后，你应该能够：

1. 画出一次会议从 React 到 SQLite、RustFS、ASR、LangGraph 的完整数据流。
2. 修改企业工作台和会议记录页面，并正确处理加载、错误和空状态。
3. 使用 FastAPI 新增接口，使用 Pydantic 维护前后端数据契约。
4. 使用 SQLite 管理结构化数据，使用 RustFS 管理二进制文件。
5. 区分 ASR 与 LLM，并独立配置两类服务。
6. 修改 LangGraph 纪要工作流和模型 Provider。
7. 先用测试复现问题，再实现修复并完成回归验证。
8. 判断问题发生在浏览器、API、数据库、对象存储还是外部模型服务。

## 3. 系统架构

### 3.1 运行时数据流

```text
┌──────────────────────┐
│ React + Ant Design   │
│ 工作台 / 会议记录    │
└──────────┬───────────┘
           │ /api
           ▼
┌──────────────────────┐
│ FastAPI              │
│ 校验、状态流转、导出 │
└──────┬────────┬──────┘
       │        │
       │        ├───────────────┐
       ▼        ▼               ▼
┌───────────┐ ┌────────────┐ ┌─────────────────┐
│ SQLite    │ │ RustFS     │ │ 外部模型服务    │
│ 元数据    │ │ 录音/导出  │ │ ASR / LLM       │
│ 转写/纪要 │ │            │ │                 │
└───────────┘ └────────────┘ └────────┬────────┘
                                      ▼
                              ┌─────────────────┐
                              │ LangGraph       │
                              │ 结构化纪要工作流│
                              └─────────────────┘
```

### 3.2 数据职责

| 数据 | 存储位置 | 说明 |
|---|---|---|
| 会议标题、状态、创建时间 | SQLite `meetings` 表 | 用于列表和状态管理 |
| 转写文本、结构化纪要 | SQLite `meetings` 表 | 纪要以 JSON 保存 |
| 原始录音 | RustFS | `recordings/{meeting_id}/source.{ext}` |
| Word/Markdown 导出 | RustFS | `exports/{meeting_id}/minutes.{docx|md}` |
| 密钥和连接地址 | `backend/.env` | 不得提交到 Git |

删除会议时，SQLite 记录、RustFS 录音和导出文件会一起删除。

### 3.3 状态机

```text
uploaded → transcribed → generated → edited → export
```

| 状态 | 含义 | 下一步 |
|---|---|---|
| `uploaded` | 录音已保存 | 开始转写 |
| `transcribed` | 已获得转写文本 | 生成纪要 |
| `generated` | AI 已生成纪要 | 人工确认并保存 |
| `edited` | 已保存人工定稿 | 导出 Word/Markdown |

## 5. 第一阶段：运行系统

### 5.1 环境准备

- Node.js 和 npm。
- Python 3.14 与 uv。
- 本地 RustFS 服务，或可访问的 S3-compatible RustFS。
- Git。

项目已经初始化 CodeGraph，无需重复初始化。

### 5.2 配置后端

在项目根目录执行：

```powershell
uv sync
Copy-Item backend\.env.example backend\.env
```

检查 `backend/.env` 中的 RustFS 地址和密钥是否与本地服务一致。默认 SQLite 文件路径为：

```dotenv
DATABASE_PATH=backend/data/meetmind.db
```

数据库目录和表会在后端首次加载存储层时自动创建。

### 5.3 启动服务

先启动本地 RustFS，再在项目根目录启动后端：

```powershell
uv run python backend\main.py
```

另开一个 PowerShell：

```powershell
cd frontend
npm install
npm run dev
```

访问地址：

| 地址 | 用途 |
|---|---|
| `http://localhost:5173` | React 前端 |
| `http://localhost:8000/docs` | FastAPI Swagger |
| `http://localhost:8000/api/health` | 后端健康检查 |
| `http://localhost:9000` | 默认 RustFS S3 API |
| `http://localhost:9001` | 默认 RustFS 控制台 |

### 5.4 首次验收

1. 使用 `demo` ASR 和 `demo` LLM 完成一次完整流程。
2. 在“会议记录”页面确认新记录出现。
3. 重启后端，确认记录仍然存在，证明 SQLite 已持久化。
4. 在 RustFS 控制台确认录音和导出对象存在。
5. 删除会议，确认列表、SQLite 和 RustFS 关联数据同步清理。

## 8. 第四阶段：SQLite 数据库

### 8.1 当前设计

项目直接使用 Python 标准库 `sqlite3`，没有引入 ORM。`MeetingStore` 初始化时执行 `CREATE TABLE IF NOT EXISTS`。

核心字段：

- `id`
- `filename`
- `title`
- `created_at`
- `status`
- `transcript`
- `minutes_json`

`save()` 使用 `INSERT ... ON CONFLICT DO UPDATE` 同时支持新增与更新。

### 8.2 学习重点

- SQLite 文件和连接生命周期。
- 参数化 SQL，避免字符串拼接。
- `sqlite3.Row` 到 Pydantic 模型的转换。
- JSON 字段的序列化与反序列化。
- 事务、索引和迁移的必要性。

### 8.3 练习

1. 使用 SQLite 工具查看 `meetings` 表。
2. 为 `status` 和 `created_at` 增加组合索引并比较查询计划。
3. 为会议列表增加后端分页参数。
4. 设计 `schema_version` 或迁移脚本，不要直接手工修改生产数据库。

### 8.4 何时升级 PostgreSQL

出现以下需求时应评估迁移：

- 多用户并发写入。
- 多实例后端共享数据库。
- 复杂全文搜索、权限关联和统计查询。
- 严格的备份、审计和高可用要求。

迁移后仍应让 RustFS 负责录音和导出文件。

## 9. 第五阶段：RustFS 对象存储

### 9.1 当前对象布局

```text
huizhi-meetings/
├── recordings/{meeting_id}/source.{ext}
└── exports/{meeting_id}/minutes.{docx|md}
```

会议元数据不再保存为 `meetings/{id}.json`。

### 9.2 重点代码

- `RustFSStorage._ensure_bucket()`：检查并自动创建存储桶。
- `put()` / `get()`：写入和读取对象。
- `list_keys()`：分页列举指定前缀。
- `delete()`：删除对象。
- `MeetingStore.audio_key()`：构造录音路径。

### 9.3 常见故障

| 现象 | 优先检查 |
|---|---|
| `403 Forbidden` | 访问密钥、桶权限、端点是否匹配当前 RustFS |
| `InvalidAccessKeyId` | `RUSTFS_ACCESS_KEY` 是否属于当前服务 |
| `Connection refused` | RustFS 是否启动、端口是否正确 |
| 首次访问桶失败 | 账号是否有 `HeadBucket` 和 `CreateBucket` 权限 |

不要把权限错误当成“桶不存在”。当前实现只在明确的 404/`NoSuchBucket`/`NotFound` 时创建桶。

## 10. 第六阶段：ASR 语音转写

### 10.1 ASR 与 LLM 的区别

- ASR：音频 → 文本。
- LLM：文本 → 摘要、关键要点、决策、行动项。

两者在「模型服务」中分别选择默认模型，互不影响。

### 10.2 当前 ASR 配置

在前端「模型服务」中添加支持 OpenAI-compatible `/audio/transcriptions` 的供应商和 ASR 模型，并设为默认。未配置默认模型时使用固定示例转写。第三方兼容服务可能不支持 `whisper-1`，必须使用该服务实际提供的模型名称。

### 10.3 请求流程

1. 从 RustFS 读取录音字节。
2. 写入带原扩展名的临时文件。
3. 关闭临时文件句柄。
4. ASR 客户端重新打开文件并上传。
5. 在 `finally` 中删除临时文件。

第 3 步对 Windows 很重要。未关闭 `NamedTemporaryFile` 就再次读取会触发 `PermissionError: [Errno 13]`。

### 10.4 400 错误排查

当外部 ASR 返回 `400 Bad Request` 时，依次检查：

1. 「模型服务」中选择的 ASR 模型是否受该服务支持。
2. 服务是否真的兼容 `/audio/transcriptions`。
3. 文件格式、文件大小和音频编码是否受支持。
4. 请求是否需要额外字段，例如语言或特定响应格式。
5. 读取服务响应正文，而不只看状态码。

### 10.5 进阶方向

- 返回时间戳和字幕分段。
- 发言人分离。
- 自定义热词。
- 长音频切片、重试和断点恢复。
- WebSocket 实时转写。

## 11. 第七阶段：LangGraph 与多模型协议

### 11.1 当前工作流

```text
START → generate_minutes → END
```

`generate_minutes` 节点负责：

1. 从模型注册表读取默认 LLM 和供应商，再调用 `build_managed_chat_model()`。
2. 未配置默认 LLM 时使用本地确定性提取。
3. 真实模型模式要求返回结构化 JSON。
4. 使用 `Minutes` 模型做最终校验。

### 11.2 Provider

| Provider | 协议 | 在模型服务中填写 |
|---|---|---|
| `openai` | OpenAI | 地址、API Key、模型名称 |
| `anthropic` | Claude 原生协议 | 地址、API Key、模型名称 |
| `ollama` | Ollama | 地址、模型名称 |
| `openai_compatible` | vLLM 等兼容服务 | 地址、可选 API Key、模型名称 |

未配置默认 LLM 时，纪要使用本地规则。旧模型环境变量不再读取。

### 11.3 练习

新增质量检查节点：

```text
START → generate_minutes → validate_minutes → END
```

检查行动项是否包含负责人和截止时间，并为合格与不合格输出分别编写测试。

### 12.3 定位顺序

```text
浏览器操作
  → 浏览器 Network / Console
  → FastAPI 状态码和异常
  → SQLite 数据是否更新
  → RustFS 对象是否存在
  → 外部 ASR / LLM 响应
```

不要把静态代码检查当成真实外部服务联调成功。测试中的 MemoryObjectStorage 和 `demo` Provider 只验证系统逻辑。

### 12.4 修复原则

1. 先写用例复现 Bug。
2. 确认测试确实失败。
3. 用最小改动修复。
4. 运行定向测试。
